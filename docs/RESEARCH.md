# ASHVECTOR: Last Signal — engineering research

Research checked 6 September 2026. This is a decision record for the current browser FPS prototype, not a claim that the complete requested production game has been delivered. Source links below are project-maintainer or platform documentation.

## Engine and platform decisions

| Area                           | Evaluation and decision                                                                                                                                                                                                                                                                                                                                                                      | Primary sources                                                                                                                                                             |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Three.js                       | Choose Three.js for a code-driven renderer with direct control over scene construction, assets, presentation, and performance. Gameplay and multiplayer remain separate shared TypeScript systems.                                                                                                                                                                                           | [Three.js](https://threejs.org/)                                                                                                                                            |
| Three.js WebGPURenderer        | Use WebGPU with its built-in WebGL2 fallback and an explicit WebGL test setting. Initialize asynchronously. Standard PBR materials fit the prototype; custom effects should use TSL/node materials. The current guide still calls this renderer experimental. ShaderMaterial, RawShaderMaterial, onBeforeCompile modifications, and the old EffectComposer stack are not drop-in compatible. | [Renderer guide](https://threejs.org/manual/en/webgpurenderer), [API](https://threejs.org/docs/pages/WebGPURenderer.html)                                                   |
| Babylon.js                     | A credible alternative with integrated Havok physics/controller, navigation, animation, audio, inspector, LOD, and postprocessing. It offers more built-in game systems; the present code already owns those systems around Three, so a migration has no demonstrated benefit at this stage.                                                                                                 | [Official specifications](https://www.babylonjs.com/specifications/)                                                                                                        |
| PlayCanvas                     | A capable PBR engine with automatic WebGPU-to-WebGL fallback. Its current graphics documentation labels WebGPU Beta. Evaluate its authoring workflow for an editor-led production; it does not justify changing this code-led prototype.                                                                                                                                                     | [Graphics](https://developer.playcanvas.com/user-manual/graphics/), [Supported browsers](https://developer.playcanvas.com/user-manual/engine/supported-browsers/)           |
| WebGPU / WebGL2                | Keep WebGL2 support. WebGPU requires a secure context, and adapter/device initialization can fail despite API detection. Profile both backends on the actual target hardware; a newer API does not itself prove higher FPS.                                                                                                                                                                  | [MDN WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)                                                                                                   |
| Rapier                         | Appropriate for server-side grenade rigid bodies and collision. Its kinematic controller supports sliding, stairs, slopes, and moving platforms but still requires game-specific movement decisions and corrected translation application. The observed player controller instead uses shared analytic terrain and architectural collision for client/server prediction.                     | [Rapier character controller](https://rapier.rs/docs/user_guides/javascript/character_controller/)                                                                          |
| Havok Web                      | A valid alternative, especially with Babylon integration. The Web runtime package is MIT licensed. Introducing a second physics runtime alongside Rapier would add work without an established need.                                                                                                                                                                                         | [Havok Web runtime](https://github.com/BabylonJS/havok), [Package/license declaration](https://github.com/BabylonJS/havok/blob/main/packages/havok/package.json)            |
| Colyseus                       | Provides rooms, lifecycle handling, schema delta synchronization, interest views, and current fixed-step prediction/reconciliation features. It remains a good growth option. The custom transport decision must not be justified by claiming Colyseus lacks prediction.                                                                                                                     | [Rooms](https://docs.colyseus.io/room), [Prediction](https://docs.colyseus.io/netcode/client-prediction), [State optimization](https://docs.colyseus.io/state/optimization) |
| Custom authoritative WebSocket | Choose Node.js plus ws for the present bounded room implementation. Shared fixed-step simulation, input sequences, prediction, interpolation, authority, and rewind remain explicit game code. Browser WebSocket has no automatic backpressure: bound queues, cap payloads/rates, inspect bufferedAmount, and disconnect sustained overload.                                                 | [WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket), [ws project](https://github.com/websockets/ws)                                                 |
| WebTransport                   | Current MDN lists this as Baseline 2026, newly available since March 2026. It supplies reliable streams and unreliable datagrams over HTTP/3. Keep WebSocket for the prototype's deployment simplicity and older-browser reach; consider datagrams after measuring transport-related problems.                                                                                               | [WebTransport API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API)                                                                                       |

The 20 Hz simulation and small room size are implementation starting points, not evidence of 64-player capacity. Measure tick duration, bandwidth, latency, client frame time, and recovery behavior before increasing capacity. Colyseus interest views also have costs: per-client encoding and full field resends when entities enter a view. Use relevance hysteresis if adopting them.

## Title check

Exact searches for `Ashvector` and `Ashvector game` did not reveal an obvious existing game title in the returned results. The selected working title is **ASHVECTOR: Last Signal**. This was a limited obvious-conflict search, not trademark research or legal clearance.

Alternative names were rejected after finding existing games: [Cinderline](https://store.steampowered.com/app/3626540/Cinderline/), [GreyWake: Project Somnium](https://store.steampowered.com/app/4931620/GreyWake_Project_Somnium/?l=english), and [Cinderwake](https://www.cinderwake.app/). These findings demonstrate why the initial names were reconsidered; they do not establish exclusivity of ASHVECTOR or the subtitle.

## Prototype scope and limitations observed in code

These observations describe the reviewed implementation, not an exhaustive final QA report. Subsequent fixes and measured results belong in the project's release notes and performance report.

- The room configuration targets **8 human connections and 16 total combatants**, using server-controlled bots to fill capacity. This is a supported configuration target; no 64-player, 100-client, or hardware FPS claim follows from it.
- The authored map is approximately **680 × 680 metres**, with eight named POIs, analytic terrain, repeated architectural building modules, enterable primary buildings, imported scenery, and local assets. It is a compact battle royale prototype rather than a production-scale military world with bespoke art for every district.
- Shared player collision is a custom architectural/terrain controller; Rapier supplies grenade physics. It is not a complete general-purpose character simulation with full animation IK, ragdolls, moving-platform support, or production-grade traversal of arbitrary imported geometry.
- Bots use server-side perception, combat decisions, obstacle avoidance, and steering. No baked navmesh or full tactical squad navigation was present in the reviewed code.
- The implemented mode is Solo. Full squads, downed/revive gameplay, vehicles, comeback arenas, persistent authenticated accounts, PostgreSQL-backed progression, and horizontal room orchestration were not present in the reviewed files.
- Eight fictional weapon definitions and selectable attachment packages exist. Attachment packages are presets, not a fully independent attachment-slot system. Firearm hit validation uses server hitscan, including the sniper category; data fields alone do not establish projectile ballistics or penetration.
- Presentation combines licensed operator/weapon/environment assets with procedural architecture, effects, transport geometry, and first-person arm forms. It does not reach a finished AAA character, animation, audio, cinematic, or bespoke environment-art standard.
- First-person actions primarily use weapon/camera transforms and simplified presentation. They should not be represented as a complete set of hand-authored reload, plate insertion, throw, and weapon-switch animations.
- Audio is synthesized Web Audio with spatial playback. The reviewed implementation is not a surface-complete recorded sound library with sophisticated occlusion or indoor acoustic simulation.
- Smoke uses an approximate volume presentation; gameplay smoke must remain visible on low presets and be considered by bot visibility checks. The review found bugs in these areas that were sent for correction; final behavior requires verification after those changes.
- Graphics use PBR materials, directional shadows, fog, and procedural effects. The reviewed world applies distance culling to architectural chunks and uses instancing for some scenery, but this is not complete asset streaming, comprehensive per-object LOD, texture streaming, or measured GPU-memory budgeting.
- Career and preferences are stored locally in browser storage. They are not secure cross-device account progression. Disconnecting releases the current player; joining a new operation is distinct from restoring an interrupted session.
- Development hot refresh can dispose the engine and close its socket because the game lifetime follows the page's mount lifecycle. Perform stable end-to-end verification without concurrent source edits; async cleanup guards are still necessary.
- No performance result is asserted here. Record actual production-browser FPS/frame times, draw calls, memory where available, server tick distributions, bandwidth, latency, and tested connection counts separately.

## Deployment considerations

The frontend can use static/CDN hosting, but the authoritative Node game service requires persistent WebSocket support. [Render's WebSocket documentation](https://render.com/docs/websocket) describes one public HTTP/WebSocket port, heartbeat/reconnection expectations, and graceful shutdown. [Free Render services](https://render.com/docs/free) have idle shutdown and ephemeral storage; they are development hosting, not a production availability guarantee.

Without deployment credentials, [Cloudflare Quick Tunnels](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/) can expose a running local game service for a temporary playable preview. They have no uptime SLA, a documented 200 in-flight-request cap, and depend on the local host and tunnel process. A tunnel URL must not be represented as durable backend deployment.
